Сначала — правила

Решения для обсуждения

Текст храним полностью

Не только цитату: исходный текст и версии. Для Telegram используем тот же текст без анализа. Историю до первого наблюдения восстановить нельзя.

Ответы компании — отдельно

Ответ разработчика и комментарии пользователей храним как связанные сообщения с собственными версиями. Изменение ответа не становится изменением текста отзыва.

Реакции — только актуальные

Предлагается хранить последние значения лайков и дизлайков. Их динамику не версионируем и не отправляем как событие. Если она нужна, добавим таблицу наблюдений.

Архив не равен новым отзывам

Первоначальная загрузка помечается backfill. События мониторинга идут в ежедневный отчёт, поздно найденные старые публикации получают отдельную пометку.

Нет удаления «по исчезновению»

Отсутствие записи в очередном сборе не доказывает удаление на площадке. Все внешние ключи — ON DELETE RESTRICT; автоматическое каскадное удаление не предусматривается.

Расписание общее

09:00 Europe/Moscow для проекта. Передача времени в БД — timestamptz; календарные периоды вычисляются по часовому поясу проекта.

Словарь данных

Таблицы и поля

Все названия и ограничения — предложение. NOT NULL — обязательное поле; NULL — отсутствие данных; identity — ID, выдаваемый PostgreSQL. JSONB используется для исходных данных и диагностики, а ключевые поля доступны обычными колонками.

ПолеТип PostgreSQLКлюч / обязательностьЧто означает

version_nointegerNOT NULL · CHECK > 01, 2, 3… внутри отзыва.
run_idbigintFK → collection_runs.id · NOT NULLВ каком запуске обнаружена версия.

texttextNOT NULLИсходный текст без пересказа.
ratingsmallintNOT NULL · CHECK 1…5Оценка пользователя.

source_edited_attimestamptzNULLДата изменения на стороне RuStore.

Ключи, индексы и правила
  • UNIQUE(review_id, version_no); индекс (review_id, version_no DESC) и индекс published_at.

  • published_at допускает NULL: неизвестная дата не подменяется датой сбора и не участвует в годовом сравнении.

ПолеТип PostgreSQLКлюч / обязательностьЧто означает

Поведение

Как меняются данные

  1. Первый импорт. Создаём запуск backfill, отзывы и первые версии. Связанные ответы и комментарии получают свои записи. События архива идут в initial-отчёт, а не в ежедневную рассылку.
  2. Повтор без изменений. По UNIQUE(source_id, external_id) находим отзыв. Обновляем last_seen и реакции. Новую версию и событие не создаём.
  3. Изменился текст или оценка. Сравниваем хеш с последней версией под блокировкой строки. Сохраняем следующую версию и одно событие в той же транзакции.
  4. Появился ответ компании. Создаём reply и reply_version, затем reply_new. Сам отзыв не получает новую версию только из-за этого ответа.
  5. 09:00 — отправка. Фиксируем состав отчёта и части текста. Создаём отдельные задания каждому получателю; подтверждённо отправленные части повторно не берём.
  6. Сбой или неполный сбор. Сохраняем корректно полученные записи, отмечаем неполноту. Поздние события включаем в следующий отчёт. При потере подтверждения Telegram используем uncertain — абсолютное отсутствие дублей в этом случае не обещаем.

Поле content_hash текущего JSON-сборщика включает ответы и комментарии. Для этой схемы при импорте потребуются раздельные хеши отзыва и каждого сообщения; копировать общий хеш в review_versions без изменения нельзя.

Что пока не включено

FAQ, тональность, боли, результаты AI-анализа, отдельная база пользователей-панелистов, история реакций и автоматическое обнаружение удаления. Их можно добавить позже, не меняя идентичность отзывов и версий.

В текущем коде ещё нет миграций этой схемы. Перед внедрением проверим уникальность, параллельные запуски, откат транзакций, повторный импорт, составные связи и доставку после сбоев. Резервные копии и секреты настраиваются отдельно от таблиц.
